# План разгрузки Redis Presence

Статус: JSON-кодирование перенесено в Rust, revision/timestamp хранятся отдельно,
ledger/outbox используют отдельные поля. Полное отделение identity от payload
и локальный cache members для обслуживания snapshot ещё не реализованы.
Projector доставки уже работает, но snapshot продолжает читать Redis.
Оценка узких мест сделана по коду;
нагрузочных замеров пока нет. Этот документ не заменяет действующие контракты.

Связанные документы: [интеграция Redis store](redis-store-integration.md),
[схема хранения](redis-store-schema.md), [attach](redis-attach-and-snapshot.md),
[snapshot](redis-snapshot.md), [apply_presence](redis-apply-presence.md).

## Цель и границы

Перенести разбор JSON, подготовку событий и обслуживание повторных snapshot
на realtime-ноды. Сократить время выполнения Lua и объём повторных чтений Redis.

Сохраняются следующие требования:

- Redis остаётся источником общего состояния; локальная проекция восстанавливается
  из него и committed events. При отказе Redis нет независимого memory fallback.
- Проверка lease и запись защищённого состояния выполняются атомарно.
- State, versions, результат операции в ledger и данные события в outbox
  фиксируются совместно; повтор сохраняет первоначальный outcome и event ID.
- Timestamp события определяется Redis. Публичное событие можно восстановить
  из неизменяемой записи outbox без чтения актуального состояния канала.
- Batch применяется целиком, snapshot согласован с изменениями канала.

Добавление realtime-нод распределяет вычисления и клиентскую рассылку.
Само по себе оно не уменьшает объём чтения и записи на одном Redis primary.
Redis sharding и переход к другой модели владения каналами сюда не входят.

## Исходные узкие места

- `attach_and_snapshot` читает всех участников через HGETALL даже при повторном
  attach без изменений, затем формирует полный snapshot.
- При потере Presence дополнительно читается индекс members соединения по всем
  каналам, разбираются JSON удаляемых участников и формируется outbox.
- `snapshot` читает payload и metadata всех участников через HGETALL; стоимость зависит также
  от общего размера JSON, а не только от числа участников.
- `prepare_presence_batch` читает только затронутых участников, но cjson разбирает
  оболочку payload ради полей идентичности. Вложенный dataJson уже не разбирается,
  но его строка по-прежнему проходит через JSON-декодер.
- Replay ledger читает все поля HASH одной операции; объём чтения по-прежнему
  зависит от числа изменений и размера сохранённых payload.

Расчёт восьми числовых полей и проверки lease не являются первыми кандидатами
на оптимизацию. Сортировка snapshot и сборка публичных событий уже вынесены в Rust.

## 1. Отделить служебные поля от пользовательского payload

Первый этап, сохраняющий доменный контракт операций.

1. Определить компактный формат метаданных участника: идентичность, поколение
   и необходимые версии. Пользовательский payload хранить отдельным непрозрачным
   значением, чтобы проверки Lua не требовали его JSON-декодирования.
2. Зафиксировать ключи/поля и правила совместного создания, изменения и удаления
   metadata и payload. Выбрать порядок перехода схемы; если старые данные уже
   используются, предусмотреть новый namespace/версию или явную миграцию.
3. Обновить mutation, snapshot и cleanup так, чтобы оба представления менялись
   атомарно. Сохранить семантику Leave без data: использовать последние данные,
   включая изменение предыдущим элементом того же batch.
4. Сохранять в outbox полные неизменяемые данные для сборки события в Rust.
   Ссылка на изменяемую запись участника вместо payload недопустима.

Результат: Lua проверяет небольшие метаданные и перемещает payload как строку;
Rust разбирает пользовательский JSON. Это уменьшает CPU и временные аллокации
Lua, но само по себе не устраняет полный snapshot и передачу его байтов.

## 2. Обслуживать snapshot из локальной проекции канала

Второй этап, после готовности outbox publisher и projector. Требует отдельного
согласования с контрактом `attach_and_snapshot`, который сейчас возвращает
состояние после attach из одного Redis-вызова.

1. Хранить на realtime-нодах проекции используемых ими каналов и обновлять их
   committed events. Описать загрузку, освобождение памяти и восстановление проекций.
2. Загружать начальное состояние из Redis, буферизуя конкурентные события;
   применять их по версиям с дедупликацией и обнаружением пропусков.
3. Определить, какие версии возвращает attach и как проекция формирует снимок,
   согласованный с ними. Учесть и Presence revision, и Occupancy version.
   Простого условия «локальная версия не меньше нужной» недостаточно, если
   требуется состояние именно на момент attach: надо согласовать последующие
   deltas, буферизацию и границу снимка.
4. При пропуске событий или отсутствии пригодной проекции выполнять resync
   из Redis; локально сериализовать снимок и рассылать его клиентам.

Результат: повторные подключения используют локальную проекцию, вместо полного
чтения канала из Redis на каждый attach. Холодная загрузка и resync сохраняют
стоимость чтения полного состояния. Обычная пагинация без согласования версий
не заменяет атомарный snapshot.

## 3. Рассмотреть подготовку batch в Rust с условным commit

Отдельное решение после оценки первых двух этапов; не обязательная часть перехода.

Предлагаемый порядок:

1. Прочитать нужные записи и признаки их версий из Redis.
2. Проверить batch и подготовить изменения на realtime-ноде.
3. Коротким Lua-вызовом проверить lease, ledger и актуальность всего прочитанного
   состояния, затем записать state, versions, ledger и outbox.
4. При конфликте перечитать состояние и пересчитать план; при неопределённом
   результате commit использовать ledger и прежнюю идентичность операции.

Одной `presence_revision` недостаточно: расчёт зависит также от attachment,
состояния соединения, счётчиков и ledger. Определить полный набор проверок
и при необходимости внутренние версии; исключить изменения, которые не видны
этим проверкам. Отдельно сохранить назначение времени Redis при commit.

Это переносит вычисления в Rust, но добавляет запросы и повторы при конкуренции.
Для горячего канала эффект может оказаться отрицательным. Принцип оптимистической
проверки описан в [документации Redis о транзакциях](https://redis.io/docs/latest/develop/using-commands/transactions/);
предлагаемая проверка и запись через Lua остаются отдельным проектным решением.

## Проверка результата

Поведенческие и нагрузочные тесты пока отложены. Перед включением оптимизаций
сравнить время скриптов и p95/p99 задержки операций, CPU/память Redis и realtime,
объём передаваемых данных, частоту resync и повторов условного commit.

Сценарии: рост канала и размера data, массовый attach/reconnect, потеря Presence,
batch с повторяющимися client ID, конкурентные изменения и восстановление ноды.
Проверить точность JSON, атомарность batch, стабильность replay, соответствие
snapshot/deltas и восстановление события из outbox после сбоя.

Следующее действие: спроектировать компактное хранение metadata и payload
участника, затем обновить схему и затронутые Lua/Rust операции.
